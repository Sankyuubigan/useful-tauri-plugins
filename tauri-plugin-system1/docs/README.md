# tauri-plugin-system1

Рантайм **быстрых решений (System-1)**: загрузка модели, жизненный цикл сессии ONNX
и инференс типизированных вопросов. Модель-агностичен: первая (и пока единственная)
модель — Laya (`mizchi/laya-multilingual-onnx`, ONNX fp16, 322M).

Стандарт проекта: `../PLUGIN_STANDARD.md`. Этот плагин следует всем его пунктам,
включая два канала доставки JS (npm `dist-js/` и vanilla `api-iife.js`).

---

## Граница ответственности

Это главное в плагине. Он **не знает предметной области**: ни невроза, ни
элементов `e1..e9`, ни порогов.

| В плагине | В хосте |
|---|---|
| пути к артефактам, загрузка ONNX Runtime | YAML критериев, тексты вопросов |
| жизненный цикл модели и сессии | пороги элементов |
| скачивание модели в `KingOrchData` + sha256 | правило `p_true >= threshold` |
| построение последовательности и батча | имя сигнала, маршрутизация графа |
| усреднение по перестановкам вариантов | UI поверх панели плагина |

Дверь наружу — три структуры из `src/contract.rs`:

```rust
DecisionRequest  { state, questions: Vec<TypedQuestion>, permutations }
DecisionResult   { answers: Vec<QuestionAnswer>, device, elapsed_ms }
TypedQuestion    { id, qtype, instructions, options: [String; 2] }
```

Хост маппит свой YAML в `TypedQuestion`, получает `p_true` на каждый `id` и сам
принимает решение по своим порогам.

## Инварианты

Три места, где ошибка была бы тихой и дорогой. На каждое есть тест.

1. **Слот 1 — всегда положительный вариант.** Вероятность читается как
   `softmax(logits)[1]`. Перестановка меняет БУКВЫ A/B, но не слоты, поэтому
   инвариант держится в любом проходе. Нарушение тихо инвертировало бы все
   вердикты. → `inference::tests::positive_option_stays_in_slot_one`
2. **Два прохода дают разные входы.** Иначе усреднение бессмысленно, а отчёт
   показывал бы стабильность, которой нет. →
   `inference::tests::passes_differ_in_letters`
3. **Пустой ожидаемый sha256 = проверки не было**, а не «проверка прошла».
   Возвращается наружу `None`, чтобы вызывающий знал. →
   `catalog::tests::empty_hash_means_no_verification_not_passed`

## Пути

Все считаются от `current_exe().parent()`, **не** от рабочего каталога и **не**
от `app.path().executable_dir()` (правило cwd в `AGENTS.md`). В dev это разные
пути, в инсталле рабочий каталог указывает в папку exe. Относительные пути
уже ломались в этом проекте: `test/laya_probe/models/...` не существует ни в
одном инсталле.

```
KingOrchData/system1/models/laya-multilingual-onnx/model.onnx
KingOrchData/system1/models/laya-multilingual-onnx/tokenizer/tokenizer.json
KingOrchData/system1/runtime/onnxruntime.dll
```

`onnxruntime.dll` ищется **в одном месте** — `KingOrchData/system1/runtime/`.
Раньше кандидатов было три (`<exe>/laya/`, `runtime/`, `%SystemRoot%\System32`),
и это было неверно:

- `<exe>/laya/` ставился установщиком через `bundle.resources`, а глобальная
  документация требует обратного: движок «**не бандлится** в приложение, он
  скачивается пользователем» (`llama_cpp_engine.md:44`, `crispasr_engine.md:41`),
  и `bundle.resources` «бандлит только `agents/`, `mcp_servers/`, каталоги и
  `*.json`» (`llama_cpp_engine.md:70-72`, `crispasr_engine.md:56-58`);
- `%SystemRoot%\System32` проверяться не должен: там встречается посторонняя
  `onnxruntime.dll`, не экспортирующая `OrtGetApiBase`, и её загрузка дала бы
  пользователю «сломано» вместо внятного «не найдено, вот путь»
  (`core/rules.md` §2.2).

Если DLL нет — ошибка в лог и наружу **с точным ожидаемым путём**, чтобы
пользователь видел, куда её положит кнопка «Скачать всё».

## Ни модель, ни движок не бандлятся

Модель весит 646 870 871 байт, ONNX Runtime — 15 809 848. Ни то, ни другое не
едет в инсталлер: каждое обновление приложения тащило бы их заново. Оба
скачиваются по требованию в `KingOrchData/system1/` — так же, как
`tauri-plugin-llama-engine` скачивает движок и `.gguf`.

Каталог с ревизией и контрольными суммами — `src/catalog.rs`. Ревизия
закреплена коммитом `d9d003d5…`, а не веткой `main`: ветка может уехать под тем
же именем, и проверка целостности станет ложной.

Скачивание идёт через `tauri-plugin-downloader` — единый движок хоста (multi-chunk,
resume, зеркало HuggingFace, событие `downloader:progress`). Свой загрузчик
означал бы второй механизм доставки файлов в том же приложении.

`onnxruntime.dll` приезжает в zip: скачивается архив
`onnxruntime-win-x64-1.28.0.zip`, из него берётся **одна** DLL, архив удаляется,
хэш распакованного файла сверяется. Версия 1.28.0 — не ниже 1.27, потому что
`ort` 2.0.0-rc.13 требует `ORT_API_VERSION` = 27.

### Автоматическая доставка

Флаг `"plugins": { "system1": { "autoDownload": true } }` в `tauri.conf.json`
включает автоскачивание: первое обращение к модели само доставит недостающее —
сначала ONNX Runtime, затем файлы модели. Флаг читается в `init()` и кладётся в
`state::AUTO_DOWNLOAD`; по умолчанию `false`.

Порядок обязателен: `provisioning::ensure_artifacts` вызывается **до**
`System1Model::load`. `runtime::init_environment` кэширует ошибку в `OnceLock`
навсегда («первая попытка провалилась — повторять нельзя»), поэтому вариант
«сначала попытаться загрузить, потом скачать, потом повторить» нерабочий: вторая
попытка получила бы тот же закешированный `Err`, даже если DLL уже на диске.

Граф workflow исполняется в синхронном потоке, а доставка асинхронная. Поэтому
`ensure_artifacts` — единственная синхронная точка входа: она поднимает
отдельный поток со своим `tokio`-runtime и ждёт его. Блокировка допустима
(граф последователен), и пул Tokio хоста не занимается. Повторный вход во время
загрузки отклоняется (`DOWNLOADING`), а не начинает второй поток на 646 МБ.

## Устройство: только CPU

Ort-CUDA требует CUDA 12 + cuDNN на машине пользователя — это системная
зависимость. DirectML уже откачен после падения `STATUS_DLL_NOT_FOUND` (жёсткий
импорт `DirectML.dll` в таблице импортов PE разрешается Windows **до** `main()`).

Тип `QuestionType` и `PermutationPolicy` — закрытые перечисления. Новый тип
вопроса или другой рантайм добавляются новым вариантом, а не флагом.

---

## Почему модель в памяти одна

`ort::Session::run` требует `&mut`, модель разделяется между вызовами — поэтому
внутри `System1Model` есть `Mutex<Session>`. Это осмысленно: блокировка защищает
**действительно разделяемую** сессию.

В хосте до переноса было наоборот: `LayaValidator::load(...)` вызывался внутри
обработчика ноды, то есть 646 МБ и токенизатор перечитывались на каждом прогоне
графа, а `Mutex` при этом защищал единственный экземпляр, который тут же
выбрасывался. Теперь модель грузится лениво и живёт до `remove_model` или смены
идентификатора.

## Команды

| Команда | Что делает |
|---|---|
| `get_status` | пофайловая проверка комплекта (`files[]`), DLL, устройство, каталоги |
| `download_all` | ONNX Runtime, затем модель; сверить sha256 каждого, снять модель из памяти |
| `download_model` | скачать только модель + сверить sha256, снять модель из памяти |
| `remove_model` | выгрузить из памяти и удалить каталог |
| `decide` | типизированные вопросы → вероятности |

Порядок в `download_all` зафиксирован на бэкенде: инференс без DLL невозможен,
поэтому качать 646 МБ модели при отсутствии рантайма — тратить время впустую.

## Фронтенд

```html
<system1-panel></system1-panel>
```

Панель показывает пофайловый чек-лист комплекта (движок / модель / токенизатор)
с размером и состоянием каждого файла, кнопки «Проверить», «Скачать всё»,
«Удалить модель» и итоговую готовность.

В хосте `king_orch_3` панель смонтирована в настройках:
`index.html` → `<template id="template-settings-lazy-panels">`.

JS доступен двумя каналами (единый источник `guest-js/`): `dist-js/` для
npm-хостов (хост импортирует `@my-tauri-plugins/plugin-system1`) и `api-iife.js`
для vanilla через `global_api_script_path`. Правки `guest-js/*` требуют
`npm run build` **и** `npm run build:global`, оба артефакта коммитятся.

Прогресс загрузки UI слушает `downloader:progress` через `onDownloadProgress`.

## Сборка и тесты

```
npm install && npm run build && npm run build:global
..\test-plugin.bat tauri-plugin-system1
```

Тесты юнит-уровня (`--lib`), без реальной модели: инварианты, каталог, пути.
Тест на реальной модели потребовал бы 646 МБ на диске — это задача хоста, а не
плагина.
