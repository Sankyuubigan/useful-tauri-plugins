# Правила сборки и релизов (Rust + Tauri) — общие для всех проектов

> Перенесено из глобальной доки `desktop_rust_tauri/rules.md` (§2 «Скрипты сборки»,
> §3 «Релизы и автообновление») с обобщением под любой проект. Эталон реализации —
> `tauri-build-toolkit` (этот пакет). Глобальная доку остаётся источником общих
> архитектурных правил; здесь — правила, относящиеся к сборке/релизу.

## 1. Скрипты сборки (build.bat / cli.cjs)

Процесс сборки запускается через `build.bat`-обёртку, которая настраивает
MSVC-окружение и вызывает Node-CLI пакета. При правке этих файлов соблюдай строгие
правила, иначе сборка упадёт с ошибками парсинга `cmd`.

### ⚠️ Ошибка «Неизвестный символ» в .bat
- В `.bat` файлах используй только **ASCII**-символы. Никакой кириллицы, смарт-кавычек или тире.
- Переносы строк — строго **CRLF**.
- Комментарии — `REM`, а не `::`.
- **Не используй `(` `)` внутри `echo`** внутри блоков `( )`.

### Очистка процессов перед сборкой
Tauri-сборка часто копирует sidecar-бинарники или перезаписывает `.exe`. Если старая
копия приложения запущена, сборка упадёт с `os error 32`.
- **Решение:** в самом начале сборки принудительно убивай процесс текущего
  приложения (`taskkill /f /im <app>.exe` с глушением ошибки). В пакете это делает
  `build` до `npx tauri build` (имя exe берётся из `appExe`, дефолт — `package.name`).

### Запрет на прямой вызов cargo / npx tauri
Если в проекте есть `build.bat`, `test.bat` и аналоги — **ЗАПРЕЩЕНО** использовать
прямые вызовы `cargo build` / `cargo test` / `cargo check` / `npx tauri build` /
`npx tauri dev`. Прямой вызов ломается из-за сброшенных переменных MSVC или
конфликтов с `sccache`. Всегда запускай сборку/тесты через командные файлы-обёртки.

### Инициализация MSVC (Обязательно!)
Любой `.bat`, запускающий `cargo` / `npx tauri build`, **обязан** инициализировать
MSVC-окружение (vswhere → `vcvarsall.bat x64`). В шаблонах пакета это уже сделано.

### Проверка ошибок в .bat файлах (Обязательно!)
После критического шага (`node cli.cjs ...`) — проверяй `%ERRORLEVEL%`. При ошибке:
сообщение + `pause >nul` + `exit /b 1`. Консоль **НЕ** должна закрываться молча.

Успешный `release` тоже не должен закрывать консоль молча: после `echo [+DONE]`
идёт печать success-отчёта (тег, продукт, установщик, URL релиза, `latest.json`,
ветка) из `lib/release.cjs`, затем `pause` — пользователь должен успеть прочитать итоги.

### Разделение сборки: dev vs installer
- `build.bat` — быстрая dev-сборка (фронтенд + Rust), **без** сборки `.exe` установщика (`bundle.active=false` в dev-override).
- `generate_installer.bat` — полная сборка `.exe` установщика (release, LTO, sidecar, иконки, версия).
- **Запрещено** добавлять сборку установщика в `build.bat` — замедлит dev-цикл.

### ⚠️ Единый источник правды для профиля сборки
- Профиль release (LTO, codegen-units, strip) определяется **ТОЛЬКО** в `Cargo.toml → [profile.release]`.
- **ЗАПРЕЩЕНО** задавать `CARGO_PROFILE_RELEASE_*` через env в `.bat`. Причина: cargo
  кладёт итоговые значения в fingerprint каждого крейта; разные env между скриптами →
  пересборка нативных крейтов (в проектах типа llm — десятки минут).
- «Сброс» — только пустыми значениями: `set "CARGO_PROFILE_RELEASE_LTO="`.
- Шаблоны пакета сбрасывают профиль-переменные и `CC/CXX/CMAKE_C_COMPILER_LAUNCHER/RUSTC_WRAPPER/CARGO_BUILD_RUSTC_WRAPPER`.

### ⚠️ Приложение не должно писать в рабочую папку (cwd)
- Пути к себе (exe_dir, папка движка, логи) вычисляй через `std::env::current_exe().parent()`,
  а **НЕ** через `app.path().executable_dir()` (в dev возвращает cwd и «насрёт» DLL в корень репо).
- Скрипт, запускающий приложение, должен задавать `cwd` на папку exe (`src-tauri/target/release`).

## 2. Релизы и автообновление (tauri-plugin-updater)

### 2.1 Ключи подписи (общие для ВСЕХ проектов)

Подписи установщиков — **одни и те же для всех проектов**. Ключи — в **общем каталоге**
глобальной документации (вне проектов). В репозиторий проекта ключи/пароли **не коммитятся**.

```
<docs>/software/настройки/tauri_signed_keys/
├─ tauri.key              — приватный ключ (НЕ коммитить, НЕ светить в docs)
├─ tauri.key.pub          — публичный ключ
└─ TAURI_KEY_PASSWORD.txt — пароль от приватного ключа
```

Механизм (в `signing.cjs` пакета):
- путь ключа: env `TAURI_PRIVATE_KEY_ORIGINAL` → `config.signing.keyPath` → env `TAURI_KEYS_DIR` → глобальный каталог по умолчанию;
- пароль: env `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` → `config.signing.password` → `config.signing.passwordFile` → `TAURI_KEY_PASSWORD.txt` рядом с ключом → env `TAURI_KEY_PASSWORD`;
- ключ прокидывается в `TAURI_SIGNING_PRIVATE_KEY` одной строкой (без переносов);
- установщик: strict=false (нет ключа → warn, сборка без подписи); релиз: strict=true (нет ключа → падение).
- публичный ключ вшивается в `src-tauri/tauri.conf.json` (`pubkey`) из `tauri.key.pub`.

⚠️ В docs **не публиковать** содержимое `tauri.key` / `TAURI_KEY_PASSWORD.txt`.

### 2.2 Синхронизация версий (правило `YY.M.P`)
- Версия (`tauri.conf.json`, `Cargo.toml`, опц. `package.json`) обновляется **единым** скриптом (`version.cjs`).
- Обычная сборка — инкремент патча `P`; при смене года/месяца счётчик сбрасывается.
- **Защита от отката:** новая версия обязана быть строго бОльшей, чем версия в `latest.json` (инцидент: откат 26.8.173 < 26.8.174).

### 2.3 Генерация latest.json (ПОРЯДОК КРИТИЧЕН)
- `latest.json` **ДОЛЖЕН** генерироваться **ПОСЛЕ** публикации релиза (`gh release create`), а не до.
  Причина: `gh release create` нормализует пробелы в имени ассета (`King Orch` → `King.Orch`).
- URL собираем **детерминированно из ЛОКАЛЬНОГО** файла установщика:
  `https://github.com/<repo>/releases/download/v${version}/${exeFileName}`.
  **НЕ** брать URL из GitHub API (round-trip может «закрепить» битый ассет, см. анти-паттерн §2.7).
- Хард-проверки перед записью (fail-fast):
  - имя exe содержит `${version}`;
  - рядом лежит `${exeFile}.sig`;
  - URL содержит версию (и в теге, и в имени файла).
- `latest.json` **НЕ** грузится как ассет релиза (только `.exe` + `.sig`).
- Endpoint: `https://raw.githubusercontent.com/<repo>/main/latest.json` (статический файл, без редиректов GitHub Releases).

#### Парсинг GitHub API
- `gh api ... --jq .assets` — весь массив, фильтрация в Node (`find(a => a.name.endsWith('-setup.exe'))`).
- **НЕ** `jq select()` с regex (Windows-шелл ломает экранирование).
- **НЕ** конкатенация `filename + ":" + url` и парсинг через `indexOf(':')` — URL содержит `:` в `https://`.

### 2.4 UI обновления (ЗАПРЕТ на auto-install)
- Кнопка "Проверить обновления" — **ТОЛЬКО проверяет**. Установка — только по явному клику ("Обновить").
- Запрещено `confirm()` для диалогов обновления — UI-кнопки.

### 2.5 Запрет на ручное редактирование latest.json
- `latest.json` — **ТОЛЬКО** через релизный скрипт. Ручная правка запрещена (маскирует баг).
- Не обновился после релиза → чини скрипт, а не файл.

### 2.6 Обработка ошибок в релиз-скриптах
- **ЗАПРЕЩЕНО** оборачивать критичные шаги (публикация, latest.json, git push) в `try-catch`, который логирует и продолжает.
- Провалился шаг → скрипт **обязан** упасть с ненулевым кодом. Пользователь должен увидеть `[ERROR]`.
- Исключение — необязательные шаги (генерация иконок), где fallback приемлем.

### 2.7 ⚠️ АНТИ-ПАТТЕРН: выбор артефакта по алфавитной сортировке
**НИКОГДА** не выбирай установщик сортировкой списка и `[последний]` / `.pop()`.

**Реальный инцидент (эталон, King Orch):** в `bundle/nsis` копятся старые `-setup.exe`.
Строковая сортировка даёт `"26.8.87" > "26.8.133"` (посимвольно `'8' > '1'`). Скрипт заливал
**старый** exe 26.8.87 в релиз 26.8.133. Все «Обновить до 26.8.133» ставили 26.8.87 → бесконечная
петля обновлений; снаружи баг незаметен (подпись валидна).

**Правила (для ЛЮБОГО скрипта публикации):**
1. **Выбор — только по точному совпадению версии** (`^<product>_<ver>_x64-setup\.exe$`, ровно одно совпадение, иначе `throw`). Никакого `.sort()`.
2. **latest.json — детерминированно из локального файла**.
3. **Хард-проверки** (см. §2.3, fail-fast).
4. **Чистка папки бандла перед сборкой** — удалять старые `-setup.exe`, чтобы не подхватить чужой артефакт.
5. Версия в конфигах — единственный источник правды.
6. **Откат — НЕ через статичный `manifest.json`.** Список релизов и `download_url` реального
   `-setup.exe` берутся из GitHub Releases API (`GET /repos/<repo>/releases`). Релизный скрипт
   **не делает** `gh release upload manifest.json`.

### 2.8 Откат к предыдущей версии (без manifest.json)
- Единый источник правды — **GitHub Releases**. Для каждого релиза ассет, оканчивающийся на `-setup.exe` (не `.sig`), `browser_download_url` → `download_url`.
- Откат: бэкап пользовательских данных → скачивание по `download_url` (проверка HTTP 2xx) → NSIS `/S` тихий запуск → завершение процесса приложения.
- `tauri.conf.json`: `bundle.windows.allowDowngrades: true`.

## 3. Сборка как отдельный процесс при релизах

- `release` убивает старое приложение, чистит бандл, собирает, подписывает, публикует через `gh release create` с **явным `--repo owner/repo`**, потом делает `latest.json`, коммитит версию + `latest.json`, пушит по автодетектной ветке и `git fetch --tags --force`.
- **Git-гард:** перед любыми git/gh операциями origin проекта обязан совпадать с `config.repo`.
  Иначе — `throw` до начала действий (никаких «релизов в чужой репозиторий»).
- Ветка для push — `git branch --show-current`, не хардкод `main`.
- `build`/`test` git **не трогают**.

## 4. Запуск сборки через opencode / CI (⚠️ АНТИ-ЗАВИСАНИЕ)

- **ЗАПРЕЩЕНО** запускать `cmd /c build.bat` (или любой скрипт, который в конце запускает GUI) **синхронно** через тул: он ждёт завершения всего дерева процессов (GUI живёт бесконечно) → зависание.
- ✅ **Правильно — `Start-Process` с редиректом вывода в файл:**
  ```powershell
  Remove-Item log\out.txt, log\err.txt -ErrorAction SilentlyContinue
  Start-Process cmd -ArgumentList '/c','build.bat' -WorkingDirectory '<proj>' `
    -RedirectStandardOutput '<proj>\log\out.txt' -RedirectStandardError '<proj>\log\err.txt' -WindowStyle Hidden
  ```
- Дальше — опрос лога до маркера завершения/`[ERROR]` + отсутствие активных `cmd`/`node`, с таймаутом.
- **Читать логи ТОЛЬКО `Get-Content -Raw -Encoding UTF8`** (PowerShell 5.1 без BOM читает как ANSI/1251 → кириллица-маркеры превращаются в мусор и поллинг вешается).

### 4.1 Рекомендованный паттерн запуска (`build.bat` по double-click)
- Сборка отдельно от запуска; запуск GUI — отвязанно от консоли сборки (`start "" "<exe>"`), чтобы GUI пережил закрытие окна. В пакете GUI запускается detached-процессом из CLI.
- `main.rs` на Windows: `#![cfg_attr(target_os = "windows", windows_subsystem = "windows")]` — чтобы в dev не было собственной чёрной консоли у приложения.
- Не путай имена: `cargo build` выдаёт бинарь по имени пакета, `cargo tauri build` (release) — по `productName`. Запускай тот exe, что реально собран.

## 5. CDP-порт для GUI-тестирования
- ⚠️ **НЕ использовать env `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`** — wry перетирает. Порт — только через `app.windows[].additionalBrowserArgs`.
- Обязателен `--remote-allow-origins=*`. Порт — ТОЛЬКО в dev (интегрирован в `devWindow` конфига), никогда в релиз.
